# AGENTS.md — instructions for coding agents

This file defines repository-level guidance for Codex and other coding agents working on `joonblee/SKPlotMaker`.

Read this file **before editing any analysis script**, then read the relevant script docstring and nearby implementation before making changes.

## 1. Repository purpose

`SKPlotMaker` is the analysis-specific post-processing layer for the CMS `NIsoMuon` workflow.  It is not a generic plotting library.

The code converts analyser ROOT outputs into the plots and templates used for background estimation, object validation, signal modelling, and the final statistical workflow.

The intended analysis flow is

```text
analyser ROOT output
      |
      v
   hadd.sh
      |
      +--> qcd_bkg_estimation.py --> NIsoMuon_SS_fit.root
      |
      +--> dy_bkg_estimation.py  --> NIsoMuon_DYJets_est.root
      |
      +--> id_eff.py / trig_eff.py / sigFit*.py
      |
      v
   plotter.py
      |
      v
final and validation plots
```

Physics behaviour takes priority over abstraction or stylistic refactoring.

## 3. Core analysis region

The main signal-region directory convention is based on

```text
OS_POGMedium_tight_BJet_NIsoDimuon
```

with corresponding SS and light-jet regions generated by the scripts.

Important current analysis choices include:

- muon ID: `POGMedium`;
- jet ID: `tight`;
- b-tag category: `BJet`;
- nominal SR sign: opposite-sign (`OS`);
- main histogram: `Dilepton_Mass`.

Do not silently substitute another working point, sign, region, or histogram.

## 4. Blinding is a hard constraint

The current repository code uses an `11 < m(mumu) < 80 GeV` blinded/search interval in the relevant SR plotting/background workflows.

Never expose blinded SR data, change the blinded range, or replace blinding with unblinded data as part of debugging unless the user explicitly requests that change.

For validation, prefer the existing unblinded SS and light-jet control regions.

When a task only concerns style, axes, labels, code structure, or another unrelated feature, keep blinding behaviour unchanged.

## 5. Background-estimation contract

### QCD

The production QCD estimate is the **same-sign-data fit**:

```bash
python3 qcd_bkg_estimation.py --mode ss-data --year <ERA>
```

The SS fit produces the central template plus normalisation and analytic-function-envelope shape variations.

`qcd-mc` is a modelling/cross-check mode.  For the current working convention, when running QCD-MC fits use the log-chi-square objective explicitly:

```bash
python3 qcd_bkg_estimation.py --mode qcd-mc --year <ERA> --fit-objective log-chi2
```

Do not replace the final SS-data QCD prediction with QCD MC unless explicitly requested.

Current QCD mass conventions:

```text
low OS/SS diagnostic region:   5 < m(mumu) < 9 GeV
excluded QCD-MC fit region:    9 < m(mumu) < 11 GeV
high/search diagnostic region: 11 < m(mumu) < 80 GeV
```

### Shared QCD anchor file

All dynamic SS anchors are stored in

```text
/data6/Users/joonblee/PlotMaker/NIsoMuon_SS_fit_anchors.json
```

and the repository also contains `NIsoMuon_SS_fit_anchors.json` as the tracked catalogue/reference state.

Multiple `ss-data` jobs can update the same JSON catalogue.  Do **not** parallelise these fits with shell `&` unless the code has first been made safe for concurrent read/modify/write access.

Atomic file replacement alone does not guarantee that multiple concurrent read-modify-write jobs preserve every anchor update.

### DY

The current production DY method is the constant normalisation-factor method (`--method nf`, also the default):

```bash
python3 dy_bkg_estimation.py --era <ERA> --blind
```

Current NF logic:

1. build the light-jet data source;
2. subtract non-DY backgrounds;
3. derive the central NF from aMC@NLO DY simulation;
4. compare with MG LO for generator modelling;
5. use `11 < m(mumu) < 80 GeV` for the MC NF extraction;
6. multiply the background-subtracted light-jet source by the central NF;
7. write `NIsoMuon_DYJets_est.root`;
8. store primitive/statistical information under `DYAux/` for later propagation.

The parameter-dependent TF method remains a cross-check:

```bash
python3 dy_bkg_estimation.py --era <ERA> --method tf --blind
```

Do not replace the final NF-based DY estimate with inclusive DY MC or the TF method unless explicitly requested.

## 7. File ownership and responsibilities

### `hadd.sh`

Purpose: merge analyser outputs into the process files consumed everywhere else.

Key rules:

- keep aMC and MG DY samples separate;
- ttbar nominal merge uses the nominal `TTLL/TTLJ/TTJJ_powheg` files only;
- keep Run-2 and Run-3 data dataset naming logic intact;
- preserve `nominal`, `RunSyst`, and `RunXSecSyst` collection handling;
- missing files are intentionally skipped rather than killing a sourced shell.

### `dy_bkg_estimation.py`

Purpose: produce `NIsoMuon_DYJets_est.root` and DY closure/diagnostic plots.

Key rules:

- NF is production central;
- TF is a cross-check;
- aMC@NLO defines central NF;
- MG LO defines generator-modelling comparison;
- preserve `DYAux/` objects because `plotter.py` consumes them;
- if changing DY uncertainty storage, update `plotter.py` in the same task.

### `qcd_bkg_estimation.py`

Purpose: produce the SS-data QCD template, QCD nuisance shapes, QCD-MC validation fits, and anchor catalogue.

Key rules:

- do not change fit objective, mass range, exclusion region, anchor priority, model envelope, or normalisation prescription silently;
- current analysis convention for QCD-MC execution is explicit `log-chi2`;
- combined-period anchor behaviour is intentional;
- preserve per-era output-template behaviour.

### `plotter.py`

Purpose: canonical final and validation plotter.

It owns:

- process loading;
- era combination;
- blinding/Asimov display behaviour;
- data-driven QCD and DY consumption;
- signal overlays;
- systematic-template loading and correlations;
- statistical/systematic uncertainty bands;
- CMS-style plotting.

When changing `plotter.py`, avoid unrelated style or physics changes.  If the user asks for one visual change, keep data sources, normalisations, uncertainty treatment, and blinding unchanged.

Use `--strict` when validating systematic changes.

### `plotter_qcdseparate.py`

Purpose: show individual QCD MuEnriched generated-pT samples separately.

One common QCD normalisation factor is applied after summing the selected eras.  This is intentional because the diagnostic is meant to preserve relative QCD pT-bin composition.

### `os_ss_comparison.py`

Purpose: compare OS/SS behaviour in QCD MC and `Data - nonQCD`.

Current subtraction convention:

```text
OS: subtract Top + data-driven DY estimate + Others
SS: subtract Top + Others only
```

Do not reintroduce inclusive DY subtraction in OS or DY subtraction in SS unless explicitly requested.

### `id_eff.py`

Purpose: self-contained muon-ID tag-and-probe fit and SF workflow.

The C++ implementation is embedded inside the Python file and compiled with ROOT ACLiC.  Do not split it into a separately maintained `.C` file unless requested.

Preserve J/psi sideband/fitting logic, eta-dependent pT binning, and the existing output structure unless the user asks to change them.

### `trig_eff.py`

Purpose: measure high-pT single-muon trigger efficiency from the current 2D analyser histograms.

The script assumes x=`|eta|`, y=`probe pT`, then projects and rebins to the reference pT binning.  Preserve object-region boundaries and binning unless explicitly asked to change them.

### `sigFit.py`

Purpose: fit signal dimuon-mass shapes and parameterise relative mass resolution.

### `sigFit_v2.py`

Purpose: extended signal workflow including interpolation, closure products, yield summaries, and signal systematic bookkeeping.

Prefer `sigFit_v2.py` when the requested task concerns signal interpolation.  Do not delete or rewrite `sigFit.py` merely because v2 exists.

## 8. Systematic-uncertainty changes must be end-to-end

`plotter.py` contains the current nuisance naming/correlation model.  Producers write ROOT templates or metadata and `plotter.py` consumes them.

If a change affects a nuisance:

1. identify the producer;
2. identify the exact ROOT path/name written;
3. identify every consumer;
4. preserve Up/Down orientation;
5. preserve era/process applicability;
6. update strict validation if required;
7. do not silently rename an existing nuisance.

Never fix a missing systematic by simply suppressing the warning unless the nuisance is intentionally inapplicable and the code explicitly records that logic.

## 9. Editing style

Prefer minimal, local changes.

When the user says to change only one thing, do not opportunistically:

- reformat the entire file;
- rename unrelated variables;
- change colours or plotting geometry;
- change histogram binning;
- change luminosity labels;
- change normalisation choices;
- alter fit functions/objectives;
- change filesystem layout;
- change blinding;
- replace data-driven backgrounds with MC;
- remove apparently redundant compatibility aliases.

Existing hard-coded values often encode an analysis decision rather than accidental technical debt.

If a refactor is genuinely required, separate pure refactoring from physics changes and make the physics behaviour demonstrably identical.

## 10. Backward compatibility

Preserve command-line interfaces whenever possible.

Before changing an option:

- search the repository for its use;
- check README examples;
- keep aliases where they already exist (`--year`/`--era`, `Run2+3`/`full`, etc.);
- avoid changing defaults unless the user explicitly asks for a new default.

When adding a new feature, prefer a new explicit option over silently changing an established production mode.

## 11. Verification expected after edits

Use the narrowest verification appropriate to the change.

At minimum:

- run Python syntax checking for edited Python files;
- run shell syntax checking for `hadd.sh` changes;
- run the script's no-argument help or `--help` if that path does not require ROOT;
- use `--dry-run` or `--inspect-hists` where available;
- if ROOT is available, run one representative era before suggesting a full multi-era loop.

For background changes, verify the output ROOT file and expected histogram/metadata keys, not only the plot image.

For systematic changes, use a representative `plotter.py ... --strict` command.

For combined-period changes, check at least one individual era and the relevant combined period.

## 12. Documentation expectations

When code behaviour changes materially, update both:

- the script's top-level docstring/help text;
- `README.md` if the production workflow or user-facing command changed.

Keep examples executable.  Do not document a hypothetical interface that the code does not support.

## 13. Default decision rule for ambiguous coding tasks

When several implementations are possible, choose the one that preserves the current analysis output with the smallest scope of change.

If a proposed code cleanup could change physics behaviour and the user did not ask for that physics change, do not make it.
